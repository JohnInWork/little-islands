# DNG Codex — интерактивные находки

Этот срез превращает окружение из декора в короткие решения без отдельного меню.
На каждом этаже есть три основные находки и один landmark-объект, каждый в своей
комнате:

| ID | Волна | Объект | Результат |
| --- | --- | --- | --- |
| `sealed-cache` | core | древний сундук | обычный/запертый/с ловушкой/проклятый/живой вариант |
| `crystal-vein` | core | живая кристальная жила | золото и `power +1` |
| `forgotten-grave` | core | проклятая гробница | заметный урон и больше золота |
| `ancient-altar` | landmark | древний алтарь | молитва (лечение 30 % и снятие статусов), подношение (золото → постоянный `+maxHp`) или ограбление (золото ценой урона, проклятия-статуса и шума) |

Когда герой оказывается рядом с находкой, у большого пальца появляется крупная
контекстная кнопка с её иконкой. Она открывает общую пиксельную панель действий,
поэтому попадать пальцем в маленький объект мира не требуется. Тап по находке
остаётся дополнительным способом подойти, клавиатура использует `E`/`Space`.
Путь не проходит сквозь объект. Панель ставит мир на паузу и показывает только
команды ближайшего объекта.

## Контракт данных

- `FIND_CATALOG` содержит только данные отображения и два языка.
- `createDungeonFinds()` использует отдельный seeded RNG-поток и возвращает
  plain data. Изменения находок не сдвигают комнаты, лут, монстров и двери.
- ID экземпляра имеет формат `find-<depth>-<roomIndex>` и стабилен для этажа.
- Находка ставится внутри не стартовой, не выходной и не surprise-комнаты,
  имеет минимум два подхода и не занимает основной маршрут или другую сущность.
- `dcss-rpg-context-actions.js` содержит единый `INTERACTION_REGISTRY` для
  находок, дверей и ловушек: match, представление и стабильное семейство команд.
- `dcss-rpg-chests.js` независимо от общего RNG определяет тип сундука,
  доступные действия, цену инструмента, урон и шум. Постоянное содержимое и
  перенос предметов принадлежат `dcss-rpg-chest-containers.js`.
- `resolveFindInteraction()` сначала проверяет живого героя, расстояние,
  актуальное состояние и риск, затем возвращает новый снимок без мутации входа.
- Сундук имеет один из пяти детерминированных типов. Обычный открывается сразу;
  запертый требует ключ, отмычки с навыком либо разрушение; ловушку можно принять
  или обезвредить; проклятие меняет здоровье на повышенную награду; живой сундук
  наказывает неподготовленное открытие. `smash`/`attack` выдают
  оставляют примерно половину содержимого, портят остаток и создают шум для
  ближайших монстров. Обычное открытие не начисляет золото автоматически:
  игрок выборочно забирает добычу из сохранённого контейнера.
- Железный ключ открывает замок любого ранга и расходуется. Взлом I/II/III
  обслуживает замки соответствующего ранга; первый ранг расходует две отмычки,
  последующие — одну. Инструменты нельзя случайно «выпить» из рюкзака.
- Гробница никогда не убивает одним подтверждённым взаимодействием: при
  недостатке HP команда недоступна и прямо объясняет причину.

## Landmark-объекты

Landmark — второй тип записи того же `FIND_CATALOG` (`wave: 'landmark'`). Первый
объект — древний алтарь `ancient-altar`; фонтан и табличка/руна добавляются по
той же схеме без нового семейства команд.

- Landmark ставится после трёх основных находок из собственного seeded-потока
  (`mixSeed(floorSeed, 'LAND')`), поэтому добавление или перенастройка landmark
  не сдвигает сундук, кристалл, гробницу, монстров, лут и двери уже сохранённых
  этажей. `MAX_FINDS_PER_FLOOR = 4`; на этаже не больше одного landmark.
- Комната landmark — не стартовая, не выходная, не surprise и не занятая другой
  находкой. Только торговец на III/VI/IX может забрать её, когда на этаже нет
  свободной ниши; тогда алтаря на этом этаже нет, а старые находки остаются.
- Каждое действие объявлено в каталоге парой `id + roll(depth, rng)`. Числа
  бросаются один раз при генерации и лежат в `find.outcomes` plain-данными с
  ключами `LANDMARK_OUTCOME_KEYS`: `costGold`, `damage`, `heal`, `healRatio`,
  `cleanse`, `rewardGold`, `rewardPower`, `rewardMaxHp`, `noise`, `status`.
  Один общий резолвер применяет их декларативно; проверки по ID объекта нет.
- `landmarkActionRules()` решает доступность до нажатия: стоимость требует
  золота (подсказка «Нужно N●»), урон обязан оставаться не смертельным
  («Слишком опасно при таком здоровье»), а чисто восстанавливающее действие
  недоступно при полном здоровье без статусов («Нечего лечить»). Резолвер
  повторно отклоняет те же случаи: `gold-required`, `unsafe`,
  `nothing-to-restore`.
- Лечение считается от эффективного максимума героя (`actor.vitals.maxHp`) и
  никогда его не превышает; `rewardMaxHp` меняет базовый `hero.maxHp`, как
  повышение уровня. Статус landmark применяется адаптером через общий
  `applyHeroStatus()`, поэтому обереги артефактов работают одинаково.
- Скин выбирается по теме главы (`skins[themeId]`, `findSkinPath()`); тёплый свет
  алтаря гаснет после использования, а сам объект остаётся в мире тусклым следом
  решения. Локальная замена спрайта в мастерской по-прежнему идёт по ID.
- В `INTERACTION_REGISTRY` одна общая запись `landmark`: имя, описание после
  осмотра, иконка, акцент и действия приходят из каталога и `find.outcomes`.
  Новые глаголы (pray/offer/plunder) добавляются в общий словарь действий.

Алтарь: `pray` — бесплатно, `healRatio 0.3` и `cleanse`; `offer` —
`costGold = 10 + 4·depth + rng(0..4)`, `rewardMaxHp = heal = 4 + depth`;
`plunder` — `rewardGold = 12 + 4·depth + rng(0..5)`, `damage = 6 + 3·depth +
rng(0..2)`, статус `poison|chilled` на `4 + min(6, depth)` секунд, `noise 6`.
Осмотр называет только вид алтаря и не предсказывает результат.

## Сохранение

Save v35 хранит `floor.resolvedFindIds` (до четырёх ID, включая landmark) и
`floor.chests`. Landmark не добавляет полей: старое
сохранение после reload видит алтарь неразрешённым, а уже разрешённый алтарь
остаётся холодным. При загрузке каждый ID
должен точно соответствовать находке восстановленного этажа, а UID предмета не
может одновременно принадлежать герою и контейнеру. Миграция v32 создаёт
детерминированное содержимое неоткрытых сундуков; старый уже разрешённый сундук
становится открытым и пустым, поэтому не выдаёт повторную награду после reload.
Полный контракт: [2D-CHEST-CONTAINERS.md](2D-CHEST-CONTAINERS.md).

## Визуальный язык

Находка остаётся частью пиксельного мира: только billboard-спрайт без цветного
квадрата, напольного ромба или вращающегося указателя. Кристалл даёт ограниченный
локальный свет. После
использования тайник/гробница остаются в мире как след решения, а истощённый
кристалл перестаёт блокировать клетку. Результат сопровождается коротким
RU/EN-toast и цветовым импульсом. Диалог действий появляется только по запросу
и не создаёт постоянной рамки вокруг объекта в мире.

## Расширение

Следующий landmark (опасный фонтан, читаемая табличка/руна, колодец) — это
данные, а не новый modal/HUD-скрипт внутри renderer:

1. Запись в `FIND_CATALOG` с `wave: 'landmark'`, локальным спрайтом, `skins` по
   темам, `outcomes: [{ id, roll }]` и RU/EN-копией (`name`, `inspected`,
   `unsafe`, `results[actionId]`).
2. Новые глаголы — в `ACTION_COPY` и `GLYPHS` реестра; при необходимости цвет
   глифа в `dcss.css`.
3. Архетип комнаты с `content.findId` в `ROOM_ARCHETYPE_CATALOG` и подходящее
   окружение в `ENVIRONMENT_ROOM_THEMES`; планировщик свяжет их сам.
4. Новый ключ исхода (например, раскрытие карты для таблички) — одна запись в
   `LANDMARK_OUTCOME_KEYS`, валидация и одна ветка общего резолвера с тестом.
5. Тесты по образцу `tests/dcss-rpg-altar.test.js`: генерация, доступность,
   атомарность, RU/EN, save/reload; затем мобильная проверка.

`Осмотреть` сообщает только то, что герой действительно увидел: состояние,
замок, механизм или печать. Оно не предсказывает награду, урон и результат
выбора. Случайность определяется при генерации, а не после нажатия. Пока
`LANDMARKS_PER_FLOOR = 1`, второй объект будет чередоваться с алтарём по этажам
из того же потока.
