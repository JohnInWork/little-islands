# DNG Codex — рецепты расширения

Прочитать `AGENTS.md`, выбрать один рецепт и его файлы. Сначала воспроизвести
сценарий, затем ограниченная правка и проверка. Не смешивать новую механику,
массовое форматирование и перенастройку всей сложности.

## Подключить навык

Контракт: [2D-SKILLS-FOUNDATION.md](2D-SKILLS-FOUNDATION.md).
Файлы: `tools/dcss-rpg-skill-content.js`, `dcss-rpg-skills.js`,
`dcss-rpg-skill-menu.js`, модуль конкретной механики и `dcss.js` для связывания.

1. Найти существующий стабильный ID и `requiresSystems`; каталог уже содержит
   40 направлений. Не создавать второй ID для того же навыка.
2. Реализовать чистый игровой потребитель: цель, расстояние/LOS, ограничения,
   результат, стоимость и сохранение изменяемого состояния.
3. Использовать или явно расширить контракт численного эффекта. Модификаторы
   складываются с ограничениями, capabilities объединяются максимумом.
4. Проверить нулевой и все три ранга, неправильные цели, смерть и повтор команды.
5. Добавить данные трёх рангов в `SKILL_IMPLEMENTATIONS`, точные system ID в
   `SKILL_SYSTEMS` только после подключения потребителя. Меню покажет готовый пункт.
6. Проверить RU/EN, уровень/очки, сохранение/миграцию, переход этажа и мобильный
   сценарий. Не подменять реализацию флагом `enabled` или тестовым fixture.

Пороги 2/4/6 и бюджет `очки + сумма рангов = уровень - 1` участвуют в валидации
save. Их изменение требует оценки старых сохранений. Очки выдаёт
`dcss-rpg-progression.js`, не анимация уровня.

## Добавить предмет или видимую экипировку

Файлы: `tools/dcss-rpg-content.js`, `dcss-rpg-rules.js`,
`dcss-rpg-player.js`, `dcss-rpg-equipment-visuals.js`,
`dcss-rpg-item-description.js`. Правила: [2D-COMBAT-BUILDS.md](2D-COMBAT-BUILDS.md),
[2D-EQUIPMENT-MAGIC.md](2D-EQUIPMENT-MAGIC.md),
[2D-ITEM-DESCRIPTIONS.md](2D-ITEM-DESCRIPTIONS.md),
[2D-ITEM-AFFIXES.md](2D-ITEM-AFFIXES.md).

1. Уникальный ID, существующий локальный icon, slot, variant, stats, rarity/weight.
   Для нового оружия — явные `weaponFamily`, `hands: 1 | 2` и профиль дальности,
   темпа и типа удара. `hands: 1` автоматически разрешает обе руки. Длинному луку,
   посоху, древковому или тяжёлому оружию задать `hands: 2`; правило само освободит
   вторую руку, пересчитает сравнение и скроет её визуальный слой. Не добавлять
   проверки ID для хвата.
2. Предмет принадлежит одному UID; слот содержит UID. Новое свойство использует
   общие правила, а не дополнительную формулу внутри интерфейса.
3. Добавить явную запись по стабильному ID в `EQUIPMENT_VISUALS`: одна и та же
   запись обслуживает paper-doll и героя в мире. Не выводить слой из позиции
   предмета в массиве и не добавлять видимую вещь без проверяемого visual.
   Для второй руки можно задать `offhandLayer`; без него renderer зеркалит
   основной слой как безопасный data-driven fallback.
   Напольная иконка автоматически обрезает прозрачные поля через
   `dcss-rpg-item-sprites.js`; не подбирать масштаб по конкретному ID. Для
   украшения выбирать реальный предметный спрайт, а не служебную `i-*` пиктограмму
   его эффекта. Wearable-пояс в мире дополняется общей формой ремня по слоту.
4. Не писать `description` или лор для отдельного ID. RU/EN-карточку строит
   `generatedItemDescription()` из `stats`, `combat`, `magic`, `useEffect` и
   других игровых данных. Новое свойство сначала получает механику, затем одну
   словарную запись; неизвестный эффект генератор не раскрывает.
5. Проверить выпадение, полный рюкзак, атомарную смену двуручного оружия,
   надевание/снятие, две руки/два кольца,
   массовый разбор, HP после смены и reload.

Количество не задавать отдельным шансом внутри runtime. Вес и редкость нового
предмета потребляет `dcss-rpg-loot-economy.js`, а общий `lootAbundance` управляет
плотностью всего этажа. Контракт и проверки: [2D-LOOT-ECONOMY.md](2D-LOOT-ECONOMY.md).
Базовый `rarity` задаёт внутренний тир для бюджета/глубины, а видимую редкость
экземпляра вычисляет материализация: без малого свойства — обычный, с одним —
магический, с `artifactPowerId` — золотой артефакт. Новый случайный affix добавлять
одной записью в `ITEM_AFFIXES`, только после реализации механики. Большую силу —
одной записью в `PROCEDURAL_ARTIFACT_POWERS`; новый лут не совмещает обе системы.
Контракт: [2D-PROCEDURAL-ARTIFACTS.md](2D-PROCEDURAL-ARTIFACTS.md).

Допустимые семейства валидирует `WEAPON_FAMILIES`. Новому топору достаточно
`weaponFamily: 'axe'`: изученный широкий удар подключится автоматически.
Новое семейство со своей специализацией требует отдельного чистого правила,
capabilities трёх рангов и runtime-теста; не проверять конкретные ID оружия.
Готовый пример серии по одной цели — `dcss-rpg-swords.js`: любое новое оружие с
`weaponFamily: 'sword'` получает навык автоматически, а конкретный UID нужен
только для честного сброса серии при смене клинка.

### Добавить неизвестную аркану

Файлы: `tools/dcss-rpg-content.js`, `dcss-rpg-identification.js`,
`dcss-rpg-item-details.js`; для книг — `dcss-rpg-books.js`, адаптер применения —
`dcss.js`. Контракт: [2D-ARCANA.md](2D-ARCANA.md).

1. Задать стабильный истинный ID, `identification: { group, tier }` и
   декларативный эффект семейства. Допустимы `potion`, `scroll`, `wand`, `book`.
   Не кодировать результат в цвете или имени.
2. Если типов стало больше, чем внешностей группы в
   `IDENTIFICATION_APPEARANCES`, сначала добавить локальные варианты.
   `itemAppearanceFor()` требует взаимно-однозначное соответствие.
3. Любой видимый UI обязан получать `itemIdentificationView()`, а не настоящий
   предмет. Неизвестному виду нельзя передавать rarity, цену, tier или эффект.
4. Применение сначала вычисляет полный результат, затем фиксирует знание,
   расходует один предмет/заряд и проигрывает события. Неизвестную аркану нельзя
   разбирать. Цена неизвестного предмета одинакова внутри семейства.
5. Книга навыка меняет только `hero.skillStudy`, никогда не `hero.skills`, и
   читается через `readSkillBook()`. Книга заклинания меняет только `hero.spells`
   через `readSpellBook()`. Свиток или жезл с новой целью сначала получает
   отдельную чистую команду.
6. Проверить одинаковые типы, два seed, reload, переход этажа, ранги Оценки,
   полезный/опасный/пустой результат, RU/EN и обе мобильные ориентации.

### Добавить заклинание или школу магии

Контракт: [2D-SPELLS.md](2D-SPELLS.md). Каталог и чистые правила находятся в
`tools/dcss-rpg-spells.js`, начальные пресеты — в `dcss-rpg-build-presets.js`.

1. Сначала добавить заклинание данными и чистой формулой, затем runtime-эффект;
   не ветвить механику по имени, иконке или ID книги.
2. Все заклинания проходят один `spellUseAvailability()`: живой забег, слот,
   Интеллект, cooldown, цель или неполное здоровье.
   `targetMode: 'nearest'` подтверждает ближайшую цель сразу, а
   `targetMode: 'actor'` обязан открыть общий `ability-targeting` и принять
   конкретный стабильный `instanceId`.
3. Поддерживаемый эффект обязан оставаться подготовленным и выключаться при
   очистке/замене своего слота. Артефактная версия объединяется отдельно.
4. Школа появляется в меню только вместе с настоящим system/capability.
   Порог Интеллекта передаётся одинаково в preview и `learnSkill()`.
5. Сохранять только знание, три слота и активные поддерживаемые ID. Cooldown,
   частицы и текущая цель в save не входят.
6. Клеточная способность использует чистый построитель допустимых клеток и
   атомарный resolver по примеру `dcss-rpg-targeting.js`: отмена и неверная
   клетка не расходуют предмет и не меняют героя.

## Добавить монстра или пассивное существо

Файлы: `tools/dcss-rpg-content.js`, `dcss-rpg-rules.js`,
`dcss-rpg-core.js`; фауна отдельно — `dcss-rpg-passive.js`.

1. Отделить новый вид от нового поведения. Спрайт не создаёт AI автоматически.
2. Стабильный ID, существующий путь, параметры, вес и глубина появления.
3. Для нового поведения проверить движение/занятость клеток, цель, LOS,
   подготовку атаки, контакт и прекращение действий после смерти.
4. Пассивное существо не добавлять в боевой массив ради отображения:
   случайный автобой не должен превращать всю фауну во врагов.
5. Проверить известный seed и reload в мире; для сохранённого генератора
   не менять карту/ID неявно.

Если новое поведение касается толпы у горлышка, расширять чистое правило
`dcss-rpg-monster-pressure.js`, а не ослаблять коллизии. Обычный pathfinding
получает первый выбор; pressure-шаг разрешён только на свободной просторной
клетке комнаты. В одноклеточном проходе нельзя обгонять переднего врага,
телепортироваться или передавать его урон стоящим сзади существам.

## Добавить устанавливаемую ловушку

Первый полный пример — `hunter-trap` и `trap-setting` в
`tools/dcss-rpg-player-traps.js`. UI и игровой цикл только передают явную команду.

1. Не выбирать клетку случайно. `playerTrapPlacementCells()` строит доступные
   соседние цели, а `placePlayerTrap()` принимает точные координаты нажатия.
2. До списания проверить живой забег, предмет, ранг, разведанную проходимую клетку,
   двери, актёров, находки, лут, декор и уже поставленные механизмы.
3. Чистая команда возвращает новую ловушку и расход; только успешный результат
   разрешает адаптеру удалить предмет из рюкзака.
4. Сохранять только ID, владельца, координату, tier и `armed/spent`. Таймер
   удержания и визуальные частицы — временное runtime-состояние.
5. Новый вид ловушки расширять отдельным профилем эффекта и тестами. Не дублировать
   режим выбора, обработку фокуса и сохранение для каждого спрайта.

## Изменить коллизии, подход к врагу или дверь

Контракт: [2D-COLLISION-DOORS.md](2D-COLLISION-DOORS.md).
Файлы: `tools/dcss-rpg-actor-collision.js`, `dcss-rpg-doors.js`, функции
движения/контакта/перехода двери в `dcss.js`; геометрия — `dcss-rpg-world3d.js`.

1. Использовать `blockingActorCells()` для текущих клеток и ближайших целей;
   `path`-строка ассета не маршрут. Удалённый участок пути не резервируется.
2. Проверять весь отрезок через `constrainActorMovement()`. Явный допустимый
   приказ движения имеет приоритет над новым замахом; заблокированный повтор
   ввода не должен отменять текущую автоатаку.
3. Обычному melee оставить одну дистанцию начала/контакта
   `canActorsMeleeContact()`. `meleeApproachPoint()` сокращает зазор внутри
   своей клетки; не разрешать вход в занятую клетку ради исправления дальности.
4. Закрывание проверять `canCloseDoor()` до мутации: тело и ближайший шаг
   резервируют проём. Сохранять определение открытой двери и одноразовый
   `triggered`; менять только текущее `opened` в конце перехода.
5. При save/regression монстров и фауны учитывать offset центра `+0.5` по
   обеим осям; v11 и карту не перестраивать из-за этой корректировки проверки.

Приёмка: hero-collision, monster-pressure, door-state, door-runtime tests; реальный подход,
блокирование/отход, контактный урон, открытие/закрытие/reload, RU/EN и мобильные
размеры. Дальше `npm run check`; не утверждать браузерный бой по одному unit-тесту.

## Изменить масштабирование

Файл: `tools/dcss-rpg-scaling.js`, контракт [2D-SCALING.md](2D-SCALING.md).

- Общий тестовый множитель `DEFAULT_DIFFICULTY`: 0.5…4, основной профиль 2.4.
  Новый забег принимает default; текущий использует сохранённое значение.
- Новая кривая требует version-dispatch и проверки миграций.
- Предмет без ручного `minDepth` получает допустимую глубину через оценку силы;
  монстр без `tier` — оценку угрозы. Не дублировать формулы в renderer.
- Проверить монотонность этажей, крайние параметры, допустимый лут и
  детерминированность. Не усиливать врагов вслед за каждым надетым предметом.

## Добавить еду или изменить голод

Контракт: [2D-HUNGER.md](2D-HUNGER.md). Числа и чистые команды находятся в
`tools/dcss-rpg-hunger.js`; предмет только объявляет
`useEffect: { type: 'food', nutrition, healing }`.

1. Не уменьшать сытость по реальному времени вне активной симуляции. Урон от
   голода наносит только `starvationToll` и только на нулевой сытости.
2. Новая еда использует `nutrition` в секундах общей шкалы, а не собственный
   таймер или проверку ID.
3. Сначала `consumeFood()` проверяет сытость/HP и вычисляет полный результат;
   только успешная команда разрешает адаптеру расходовать предмет.
4. Штрафы входят в общий `deriveHeroStats()`, поэтому бой, движение, HUD и карточка
   не получают отдельных формул.
5. Проверить три порога, ноль, полную сытость, паузу, hidden, RU/EN, save/reload и
   старую версию. Мясо расширять через `dcss-rpg-survival.js`, не через особую
   ветку голода.

## Добавить добычу животного или рецепт костра

Файлы: `tools/dcss-rpg-passive.js`, `dcss-rpg-survival.js`,
`dcss-rpg-game-commands.js`, `dcss-rpg-context-actions.js`; адаптер — `dcss.js`.

1. Мирное существо не является целью боя, пока `hunt-wildlife` не примет его
   стабильный `instanceId`. Новый вид задаёт HP, защиту, мясо, `flee|fight` и
   числа атаки данными каталога.
2. Изменение проходит через `createGameCommand()` и чистую функцию. Она возвращает
   `{ ok, state, events }`; DOM, частицы и звук читают события только после успеха.
3. Динамическая добыча использует `transactStackItems()`: входы проверяются до
   результата, стек не расходуется частично, UID результата детерминирован.
4. Рецепт задаёт входной и выходной item ID, а не меняет массив рюкзака напрямую.
   Для новой готовой еды применяется обычный `useEffect.type = 'food'`.
5. Добавить RU/EN в общий словарь описаний и действие в `INTERACTION_REGISTRY`.
   Не создавать отдельную панель или постоянную подсветку объекта.
6. Проверить спокойное состояние, повтор охоты/смерти, полный рюкзак, reload,
   сложность разных этажей и обе мобильные ориентации.

## Добавить интерактивную находку

Контракт: [2D-ENVIRONMENT-FINDS.md](2D-ENVIRONMENT-FINDS.md).
Файлы: каталог и чистая команда в `tools/dcss-rpg-finds.js`, специализированные
правила открытия в `dcss-rpg-chests.js`, постоянное содержимое в
`dcss-rpg-chest-containers.js`, запись в `INTERACTION_REGISTRY`
из `dcss-rpg-context-actions.js`, генератор/save в `dcss-rpg-core.js`,
визуал и прямой тап по объекту в `dcss.js`.

1. Добавить стабильный ID, существующий локальный спрайт, цвет/символ и RU/EN.
2. Результат рассчитывать в чистой команде до мутации героя и валюты; отказ,
   смерть, расстояние и повторное использование не должны менять состояние.
3. Опасность обозначать до действия. Невидимый мгновенный смертельный исход
   запрещён; первая версия гробницы не разрешает смертельное взаимодействие.
4. Объект занимает одну комнату и одну клетку, не блокирует обязательный путь,
   старт, выход, дверь, событие, лут или другого актёра.
5. Записывать разрешённый стабильный ID в `resolvedFindIds`; новое поле или новый
   формат ID требует миграции и строгой валидации.
6. Добавить одну запись `match + present + command` в `INTERACTION_REGISTRY`,
   а не новую HUD-кнопку или отдельный modal shell. Если семейство команды новое,
   добавить один обработчик в `CONTEXT_COMMAND_HANDLERS`. Runtime повторно
   проверяет цель и ресурс перед мутацией.
7. Проверить множество seed, reload, оба языка и попадание по самому объекту в
   портретном и горизонтальном режимах. Не добавлять отдельную HUD-кнопку.

Для хранилища использовать отдельный массив floor-state и атомарные команды
переноса по образцу [2D-CHEST-CONTAINERS.md](2D-CHEST-CONTAINERS.md). Предмет вне
героя не должен оставаться в `run.items`, а содержимое нельзя перебрасывать при
каждом открытии.

## Сообщить итог: что получил или потерял герой

Файлы: `tools/dcss-rpg-feedback.js` (решение), `dcss.js` (`showLootToast`,
`TEXT_ICONS`, `fillTextWithIcons`), `dcss.css` (`.loot-toast`).

Правило на всю игру: итог называет, **что** пришло или ушло, — значком и словом,
не голым числом. Строка ставит метки `{gold}`, `{heal}`, `{maxhp}`, `{attack}`,
`{food}`, `{map}`; удобнее всего собрать её через `formatDeltas({ gold: 5,
attack: 1 })` → `+1 {attack} · +5 {gold}`. Переходник рисует значок, а во
всплывающей строке добавляет слово («+5 [монета] золота»). Новый ресурс — новая
запись в `TEXT_ICONS` (путь, RU, EN; `spoken: true`, если значок сам не
объясняет себя). Число над героем (`addCombatGlyph`) несёт ту же метку в конце —
`+12{heal}` — и рисует значок рядом с цифрами. Урон по существам остаётся
числом.

Вызов: `showLootToast(картинка, строка, kind)`. `kind` говорит, что случилось
(`gold`, `heal`, `buff`, `skill-up`, `spell`, `item`, `restore`, `damage`,
`trap`, `poison`, `curse`, `skill-down`, `loss`, `hostile`, `refused`, `info`…);
без него вид выводится из знаков у меток. Хорошо это или плохо, какой звук
(только из уже записанных) и какая вспышка — решает одна таблица
`FEEDBACK_KINDS`, а не место вызова. Строка итога стоит над всеми окнами
(`z-index: 35`), хорошее «хлопает» ступенчатой анимацией, плохое бьёт красной
встряской; `prefers-reduced-motion` оставляет только цвет.

## Новое поле сохранения

Файл: `tools/dcss-rpg-core.js`, адаптер чтения/записи в `dcss.js`.

1. Определить владельца: герой, текущий этаж, предмет, настройка или временная
   анимация. Последнюю не сохранять.
2. Добавить строгую схему и миграцию только отсутствующего известного поля.
   Явный мусор отвергается, будущий формат не угадывается.
3. Добавочный перенос не перестраивает этаж и не меняет сложность; прежние
   несовместимые версии используют явный исторический migration-dispatch.
4. Проверить старый/новый/corrupt/future snapshot, backup, roundtrip, смену этажа
   и повтор миграции. Не сохранять функции, DOM и Three.js-объекты.

## Заменить спрайт без изменения механики

`npm run sprites:manifest`.
