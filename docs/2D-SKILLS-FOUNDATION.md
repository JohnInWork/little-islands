# 2D-RPG — фундамент навыков

Статус: общая основа подключена к 2D-игре, опыту, характеристикам, сохранениям
и экрану персонажа. Первый игровой срез — **Чутьё** (`trap-sense`) — завершён
локально: реальные обнаружение, управление, изучение и save v11 проверены в браузере.
В production зарегистрированы только Чутьё и `trap-detection`. Остальные
39 направлений пока не реализованы и скрыты; их каталог не означает, что
приручение, ремесло или обезвреживание уже доступны.

Дизайн всех направлений: [2D-SKILLS-PROPOSAL.md](2D-SKILLS-PROPOSAL.md).
Сетевые границы: [MULTIPLAYER-FOUNDATION.md](MULTIPLAYER-FOUNDATION.md).

## Правила прогресса

- 40 стабильных ID, шесть категорий, названия и описания RU/EN.
- Три ранга на навык. Минимальные уровни героя для рангов I/II/III — 2/4/6.
- На уровне 1 нет очков. Каждое повышение уровня приносит одно очко; ранг стоит
  одно очко. Очки относятся к забегу, сохраняются между этажами и сбрасываются
  при новом забеге. Отдельного опыта за повторение действий нет.
- Нет классов, обязательных порогов характеристик и случайного выбора трёх
  вариантов. Когда механики будут готовы, игрок выберет из доступного каталога.
- Снаряжение не выдаёт неявно изученные ранги. Дополнительные свойства вещей
  подключаются через собственные проверяемые правила.
- Учить можно только готовый навык в живом забеге. UI делает это в открытом
  экране персонажа, где симуляция стоит на паузе.

Пороги 2/4/6 — начальный баланс, но участвуют в валидации сохранений. Их изменение,
переименование ID, цены ранга или схемы очков требует проверки старых сохранений
и при необходимости новой миграции. Не редактировать эти числа как чисто
визуальный текст.

## Состояние и команды

Пример `hero.skills` для героя уровня 4, изучившего один ранг:

```js
{
  version: 1,
  points: 2,
  ranks: { 'trap-sense': 1 },
}
```

Это пример распределения очков, не начальное состояние героя.
Инвариант: `points + сумма изученных рангов === hero.level - 1`.
Неизвестные ID, лишние поля, дробные/отрицательные очки, невозможные ранги и
ранг выше допустимого уровня отвергаются. Для уровня 1…999 бюджет — 0…998.

- `createSkillState(level)` создаёт пустой набор рангов и `level - 1` очков.
- `grantSkillPoints(state, fromLevel, toLevel)` проверяет старый бюджет и
  возвращает новую копию. Повтор перехода с уже изменённым состоянием отклоняется.
- `awardHeroExperience({hero, amount, equipment, items})` — единая точка
  начисления XP/уровней/очков. Не выдавать очки из анимации повышения уровня.
- `skillAvailability({state, heroLevel, runStatus, skillId, expectedRank})`
  возвращает одну и ту же проверку для UI и изменения состояния.
- `learnSkill(...)` применяет следующий ранг атомарно: новое состояние и событие
  `skill-learned`, либо отказ без расхода очков. `expectedRank` защищает от
  повторного клика со старым рангом.

Событие содержит стабильный `skillId`, прежний/новый ранги и расход очков.
Это граница для будущей авторитетной команды, **не сетевая реализация**, журнал
команд или универсальный механизм защиты от повторной доставки по сети.

## Как эффекты участвуют в правилах

`SKILL_IMPLEMENTATIONS[id]` содержит только данные:
`{version: 1, modifiersByRank: [r1, r2, r3], capabilitiesByRank: [r1, r2, r3]}`.
Каждая строка — полный эффект текущего ранга, а не прибавка к предыдущим строкам.
У каждого из трёх рангов должен быть ненулевой проверяемый эффект; пустая
реализация не считается готовой.

- `deriveSkillModifiers()` складывает модификаторы разных навыков в стабильном
  порядке ID, затем ограничивает результат через `SKILL_MODIFIER_LIMITS`.
  Контракты: `attack`, `defense`, `maxHp`, `moveSpeed`, `attackSpeed`.
  `deriveHeroStats()` прибавляет их к экипировке и применяет общие ограничения
  характеристик. Меню и бой получают итог из одного расчёта.
- `deriveSkillCapabilities()` берёт максимум по каждому целочисленному полю,
  затем ограничивает его через `SKILL_CAPABILITY_LIMITS`. Сейчас предусмотрены
  `trapDetectionRadius`, `trapDetectionTier`, `trapDisarmTier`,
  `trapPlacementTier`. Первые два потребляет `discoverTraps()`; обезвреживание
  и установка пока подготовлены только как численные контракты.
- Неизвестные ключи, функции, неконечные числа и значения вне заданных границ
  недопустимы. Новый тип способности требует явного контракта и реализации,
  а не добавления произвольного ключа в сохранение.

Если изученный навык временно потерял реализацию или требуемую систему, ранг
сохраняется и продолжает учитываться в потраченных очках. Эффект не применяется,
пункт скрыт в меню. Автоматического удаления ранга и возврата очков нет.

## Совместимость сохранений

Текущий формат — **v11**, ключ `little-islands:dcss-rpg:v11`; у него отдельная
резервная копия. В `floor.detectedTrapIds` хранятся ID обнаруженных ловушек;
срабатывание по-прежнему хранится в `floor.resolved` как результат события.

- **v9/v10 → v11 — добавочная миграция.** Весь этаж, seed, координаты, открытые
  двери, собранный лут, раненые монстры, пассивные существа и выбранная сложность
  сохраняются точно. v9 получает отсутствующее состояние навыков; v10 обязан
  уже иметь валидное `hero.skills`. Ловушки на ранее разведанных клетках
  отмечаются обнаруженными: видимые в старой версии опасности не исчезают.
  Генератор и баланс не перезапускаются.
- **v1–v8 → v11** сохраняют прежний путь перехода через несовместимые поколения
  генератора/баланса: герой и вещи сохраняются, текущий этаж строится заново
  у входа, применяется актуальный основной профиль сложности. Это прежний
  rebase из v9, а не новый побочный эффект навыков.
- Старому герою v1–v9 уровня N без `skills` выдаётся N−1 нераспределённых очков.
  Если поле уже явно присутствует и повреждено, оно не заменяется новым молча.
- Новый v11 требует валидное `hero.skills` и массив `floor.detectedTrapIds`;
  дешёвая валидация autosave проверяет форму ID, гидратация проверяет точные
  ссылки на ловушки полного сгенерированного этажа. Загрузка, backup и переход этажа
  используют ту же валидацию. Состояние навыков копируется без общих изменяемых
  ссылок. Отключение реализации не делает валидный изученный ранг испорченным.

## Первый потребитель: Чутьё

Пример реализации: [dcss-rpg-traps.js](../tools/dcss-rpg-traps.js).
`trapsFromDungeon(dungeon)` получает ловушки из уже размещённых `blade-trap`;
не меняет RNG, координаты, таблицу событий и сохранённые ID. Сейчас все они
одного вида `blade`, сложности 1. Более сложные механизмы ещё не добавлены.

Чутьё I/II/III даёт радиус 2/3/4 клетки и допустимую сложность 1/2/3.
Расстояние — `abs(dx) + abs(dy)`, не экранные пиксели. Без навыка эти
capabilities равны нулю: автоматического обнаружения нет.
Без навыка вблизи остаётся слабый наземный признак механизма; плавающего значка
и света, выдающего скрытое место издали, нет. Это визуальная подсказка, не
запись в `detectedTrapIds` и не гарантированная защита от наступания.

`discoverTraps({traps, origin, capabilities, detectedTrapIds, resolvedEventIds,
hasLineOfSight})` возвращает упорядоченный список известных ID, сохраняя прежние.
LOS использует текущую сетку дверей: стена, закрытая дверь и закрытый угол
прекращают обнаружение. Потраченные механизмы больше не обнаруживаются как
новые; знание уже найденных остаётся после их удаления из runtime-событий.

`activeDetectedTrapCells()` возвращает только известные несработавшие клетки
для обхода. Скрытая ловушка не должна менять путь до обнаружения и тем самым
выдавать своё место. Обнаружение не разряжает механизм и не даёт награду.

Адаптер `discoverNearbyTraps()` пересчитывает знание после исследования,
открытия двери и изучения навыка. Если текущий маршрут пересекает новую опасность,
он прерывается; следующие автоматические пути обходят известную клетку.
Тап по далёкой ловушке не разрешает пересечь её. Перед соседней известной
ловушкой прямое управление сначала предупреждает; намеренно наступить можно
после отпускания и нового нажатия на ту же клетку. Удержание стика или повтор
клавиши ОС не считаются новым подтверждением. Этот контракт отдельно хранится
в `dcss-rpg-hazard-input.js`, а не размножается в обработчиках разных устройств.

## Рецепт: подключить следующий навык

Следующие механики — Сапёр и Ловушечник. Начать с одного целевого действия.

1. Найти стабильный ID и `requiresSystems` в каталоге. Для первого среза:
   работающий пример `trap-sense` → `trap-detection`; следующие ID:
   `trap-disarming` → `trap-disarming`,
   `trap-setting` → `trap-placement`.
2. Реализовать игровую механику-потребитель в чистом модуле: цели, дистанции,
   LOS, результат и стоимость действия. Подключить её к runtime. Для новых
   объектов добавить стабильные ID, сохранение и восстановление состояний.
3. Использовать существующий capability/modifier или расширить его явный
   контракт в `dcss-rpg-skills.js`. Проверить нулевой ранг и все три изученных
   ранга на реальном действии, включая ошибочные/недоступные цели.
4. Только после подключения потребителя добавить его точный system ID в
   `SKILL_SYSTEMS` и три строки полного эффекта в `SKILL_IMPLEMENTATIONS`.
   Требуются обе части; один флаг `enabled` не заменяет работающую механику.
5. Проверить RU/EN-описание и игровой отклик. Готовый пункт автоматически
   появится в разделе навыков экрана персонажа; модель и кнопка связаны с
   общей покупкой. Временный fixture нельзя оставлять production-реализацией.
6. Прогнать изучение/улучшение, недостаток очков/уровня, повтор команды,
   сохранение/загрузку, переход этажа, смерть, отключение реализации и сочетания
   с экипировкой. Затем мобильный экран, паузу, фокус и `npm run check`.

Для проверки готовности в изолированном тесте можно передать собственные
`implementations` и `systems` в чистые правила/модель. За референс взять
производственные строки Чутья: пустые модификаторы, радиусы 2/3/4 и tier 1/2/3.
Тестовый fixture не регистрировать вместо потребителя нового действия.

Не создан универсальный trigger engine для ответных ударов, цепной магии или
спутников. Эти механики будут отдельными небольшими потребителями с ограничениями
повторных эффектов, затрат и контроля врагов. Общая основа отвечает за изучение,
хранение и согласованные значения, а не автоматически реализует все описания.

на отдельном QA origin без очистки сохранений пользователя.
